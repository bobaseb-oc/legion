# Always-on gaps — implementation plan (L1 and L3 RED ZONE DRAFT)

Spec: `docs/superpowers/specs/2026-11-20-always-on-design.md` (Option A, with its steel-man amendments 1–4).
Open questions: `work-tasks/2026-11-20/open-questions.md` rows 16–27 (resolved), 28–34 (new, see the end).
Jira: PLP, one epic under PLP-2884's area, four tickets. Delivery: one `gh stack` on the upstream repo.

**Goal.** Make Legion's waits and deliveries survive a restart without letting disk authorize
anything: approvals re-shown after a restart (L1), notes Unii keeps beyond the transcript (L2), one
durable event inbox with source-trust classes (L3), and a paced GChat outbox (L4).

**Architecture.** Four pure modules, each unit-tested in its own `*.test.ts`, plus thin glue:

| Layer | Pure module (new) | Glue (existing) | Persistence |
|---|---|---|---|
| L2 notes | `Notes.ts` | `Tools.ts` (`notes` tool, Unii only), `Server.ts` (`Chat.call` block, `note` act, `Chat.state`), `View.ts`, `web/src/Pages.ts`, `Deck.ts` | files under `UNII_DIR/users/<id>/notes/` |
| L1 approvals | `Pending.ts` | `Tools.ts` (`ask_user`, `appeal`, `review`, `consents`), `Server.ts` (`Chat.open`, `Chat.end`, `consent` act), `Memory.ts` | view.json `pending`, `pended` |
| L3 inbox | `Events.ts` | `Server.ts` (`Chat.drain`, `event` act, `consent` act, `Chat.bridged`, `Chat.join`, `Chat.ticked`), `Memory.ts` | view.json `events`, `evented` |

**Tech stack.** Bun + TypeScript, flat repo root, colocated tests. No new dependencies.

- **Core invariant (RED ZONE, ADR 1): nothing read from disk authorizes anything.** A record read at
  load only produces a request shown to the user again. Only a live user act (`consent`, in `SAYS`,
  Server.ts:257) creates a grant. Grants are one-shot, bound to
  `fp = sha256(who \0 tool \0 canon(args incl. device))`, expire after `GRANT_MS`, live in memory only.
- **Shown text comes from the hashed args (amendment 2).** The spec's `Pending.what` is dropped.
  The record stores `args` (the canonical JSON that `fp` hashes); the pane and GChat render
  `Tools.shown(tool, JSON.parse(args))` (Tools.ts:739).
- **Event source comes from auth, never the payload (amendment 3).** `src` is set from `says`
  (`Cloud.speaks`, Cloud.ts:219) and the socket's `device`, never from a field the caller sends.
- **Disk never says yes for events either.** An approval event found `new` or `taken` at load
  becomes `done`; its request is re-shown.
- **One writer.** view.json is written only by `Memory.save` (Memory.ts:413) in the process that holds
  `Main.lock` (amendment 4). New lists are capped; malformed entries are dropped at load.
- Tests: only `bun run test [files]` (wraps `test/run.sh`, isolated temp HOME and UNII_DIR). Never
  bare `bun test`. Tests that bind ports (`Tools.base`, spawned servers) need the sandbox off.
  Baseline: 2 known failures in `local/prime/logs.test.ts` (mtime precision), not caused by this work.
- Server-level tests: the spawned-bun-script pattern (Todo.test.ts:14, Server.test.ts:1003): a
  script string run with `UNII_DIR` set to a temp dir prints one JSON line. A restart is simulated
  by a **second spawned process on the same `UNII_DIR`**.
- Load guards: Memory.test.ts `loaded(saved)` (Memory.test.ts:18).
- RED ZONE: L1 (who may approve or start unattended work, R4), the L3 trust classes, and L4 Task 14
  (a GChat reply may answer an approval, row 29). Those tasks
  are marked RED ZONE DRAFT: the human reviews and signs off before merge. Commit messages of
  those layers include `RED ZONE DRAFT`.
- Amendment 1: no L1 code starts until the `feat/risk-reviewer` layer (6e150b5) is approved by the
  user. The appeal semantics L1 persists are frozen at that point.
- Iteration caps (`policies/iteration-caps.md`): at most 3 run → analyze → edit cycles per failing
  test. On the 3rd failure stop and return `cap_hit`, `test_bug` or `ac_ambiguity`. Fixing a
  test-authoring typo does not count as an iteration.
- Diffs: a task marked **[>300 lines: checkpoint]** stops for a human look after its tests are red
  and again after green, before its commit.
- Style: namespace-style `export function` modules, terse comment-heavy headers (see Gchat.ts:1-13),
  RED ZONE comments in the form `// RED ZONE (<id>, DRAFT awaiting the user's sign-off): ...`.
- Commits: `<ticket key>: <type>: <imperative>` (`policies/commit-msg.md`), one logical change each.
  No model attribution in commit messages (coding-assistant policy).

**L2 placement: directly above `feat/risk-reviewer`.** Reasons: (1) amendment 1 blocks only L1, so L2

review; (3) L2 and L3 both edit `Chat.act` and `Chat.state` in Server.ts, so landing L2 first means
L1, L3 and L4 rebase onto it once. Cost: L2 cannot merge before `feat/risk-reviewer` merges. If that
cost is too high, the alternative is L2 as its own one-layer stack on `main`.

Each layer is one PR, independently revertable: L1 reverts cleanly if L3/L4 are reverted first;
L2 reverts alone.

## Layer L2 — Notes memory beyond the transcript (ticket 1 of 4; independent)

**Ticket summary:** `Add notes Unii keeps across runs, fenced and user-editable` (≤80 chars).
**Risk:** medium (persistent prompt-injection surface). Not RED ZONE, but the `note` act's device
refusal is an access-control check: the human reads that hunk before merge.
**Files:** `Notes.ts` (new), `Notes.test.ts` (new), `Tools.ts`, `Tools.test.ts`, `Server.ts`,
`Server.test.ts`, `View.ts`, `web/src/Pages.ts`, `Pages.test.ts`, `Deck.ts`, `Deck.test.ts`, `web/app.js` (rebuilt).
**Out of scope:** agent todos and task progress (PLP-2895, row 18); a new instructions file (row 27);
notes for agents other than Unii; editing notes in the terminal (the terminal lists them read-only, OQ 34).

### L2 invariants
- N1 Only Unii (`who === "main"`) writes notes through the tool; any other agent is refused.
- N2 A note name must match `NAME`; anything else (`../x`, `a/b`, `.x`, upper case, empty, > 48 chars) is refused before any file call.
- N3 Note text is passed through `redact(text, [])` before it is written; the file is mode 0600, the dir 0700.
- N4 The notes dir or a note path that is a symlink is refused (`fs.lstatSync`), so a planted link cannot redirect a write.
- N5 The index reaches Unii only inside `Google.fence("notes", …, "Notes Legion wrote earlier")`, never as instructions.
- N6 The `note` act (edit or drop) is refused from any device socket (`device !== ""`), as `Chat.pin` (Server.ts:1670) is.
- N7 Caps: index ≤ `NOTE_INDEX` bytes (cut, with a "… N more notes" line), note ≤ `NOTE_TEXT` bytes (refused, not cut), ≤ `NOTES` notes (refused).

### L2 acceptance criteria (Given/When/Then; one assertion each)
- L2-AC1 Given notes `a` and `b` written by Unii, when `Chat.call` builds Unii's blocks, then one block's text starts with `<untrusted source="notes">` and contains both index lines.
- L2-AC2 Given the `notes` tool, when Unii calls it with `{ write: "../x", text: "t" }`, then the result is `{ fail: true }` and no file outside `notes/` exists.
- L2-AC3 Given a note text holding `sk-ant-api03-` followed by 40 letters, when Unii writes it, then the file on disk contains `[REDACTED:` and not the key.
- L2-AC4 Given a sub-agent `Wkr`, when it calls the `notes` tool to write, then the result text says only Unii writes notes and `fail` is true.
- L2-AC5 Given `Tools.list(tools, "Wkr")`, when its names are read, then `notes` is not among them.
- L2-AC6 Given a written note, when `fs.statSync(file).mode & 0o777` is read, then it equals `0o600`.
- L2-AC7 Given `notes/` replaced by a symlink to another dir, when Unii writes a note, then the result is `{ fail: true }` and the target dir is unchanged.
- L2-AC8 Given note text of `NOTE_TEXT + 1` bytes, when Unii writes it, then the result is `{ fail: true }`.
- L2-AC9 Given 40 notes whose index lines total more than 2048 bytes, when the index is built, then its byte length is ≤ 2048 and its last line names how many notes were left out.
- L2-AC10 Given a note `plan`, when a view sends `{ $: "note", name: "plan", drop: true }`, then `Chat.state(chat).notes` no longer lists `plan`.
- L2-AC11 Given a note `plan`, when a device socket sends `{ $: "note", name: "plan", text: "x" }` (device `"mac"`), then the answer has an `error` and the file is unchanged.
- L2-AC12 Given a view's edit `{ $: "note", name: "plan", text: "new" }`, when the file is read, then it holds `new` and Unii's next blocks show the new line.
- L2-AC13 Given state with two notes, when the web Memory page renders (`Pages.memory_html`), then it holds a Notes section with an Edit and a Drop control per note.
- L2-AC14 Given state with two notes, when the terminal Memory page draws (`Deck` memory parts), then both note names are listed.
- L2-AC15 Given a note file planted by hand with a valid name, when `Chat.state` runs, then it is listed (the user sees what Unii will read).

## Layer L1 — Durable approvals (ticket 2 of 4; RED ZONE DRAFT, R4, ADR 1)

**Ticket summary:** `Persist approvals across restarts; only a live yes grants a one-shot run` (≤80 chars).
**Gate:** do not start until the user approves the `feat/risk-reviewer` layer (amendment 1).
**Risk:** high. Wrong code here lets a forged file, a replay or a changed call run without the user.
**Files:** `Pending.ts` (new), `Pending.test.ts` (new), `Memory.ts`, `Memory.test.ts`, `Tools.ts`,
`Tools.test.ts`, `Server.ts`, `Server.test.ts`, `work-tasks/always-on/mutate-l1.ts` (untracked).
**Out of scope:** GChat posting and answering of approvals (L4, Tasks 12 and 14); the inbox (L3); chat moves between
processes (spec "Not doing"); replaying a call from the server (rejected, row 20).

### L1 invariants (each one has a test that fails without it, and a mutant in Task 7)
- P1 A record read from disk never resolves a wait and never creates a grant. A record read with `state: "yes"` stays a closed record: it is not re-shown, makes no grant, runs nothing. Only `open` records are re-shown.
- P2 A grant is created only inside the `consent` act path (`Chat.consented`), which `SAYS` gates (Server.ts:257, 1409).
- P3 A grant is one-shot: `Pending.take` deletes it on first use.
- P4 A grant is bound to `fp = sha256(who \0 tool \0 canon(args))`; any change in who, tool, an arg or the device misses it.
- P5 A grant expires `GRANT_MS` after it is made.
- P6 A consent record expires `CONSENT_MS` after it is made: at load it becomes `expired`; live, its timer answers no.
- P7 An appeal record open at load becomes `cut` (= no); no appeal resolver exists after a restart.
- P8 Shown text is `Tools.shown(tool, JSON.parse(args))`; the record has no `what` field; a record whose `fp` does not equal the hash of its own `who`, `tool`, `args` is dropped at load.
- P9 A grant skips only the reviewer: `Tools.moded` (Tools.ts:896) still runs before it, and the device's `Hooks.pre` and guards (Machine.ts:218) still run after it.
- P10 A chat that ends (`Chat.end`) leaves its open consent records open, so the next process re-shows them; a user's stop closes them as `no`.

### L1 acceptance criteria
- L1-AC1 Given a consent opened in process A, when process B opens the chat on the same `UNII_DIR`, then `Chat.state(chat).calls` lists it with the same id, who and tool.
- L1-AC2 Given that re-shown consent, when a view sends `{ $: "consent", n, yes: true }`, then the answer is `{}`.
- L1-AC3 Given that yes, when the same agent calls the identical tool with identical args, then `AskAI.ask` is not called for a review and the result text does not contain `refused`.
- L1-AC4 Given that grant used once, when the identical call is made again, then `Chat.state(chat).calls` lists a new waiting call.
- L1-AC5 Given a granted call, when the same agent calls it with one arg changed (`command: "make deploy2"`), then a new waiting call is listed.
- L1-AC6 Given a granted call, when the identical call is made on another device (`device: "pc"`), then a new waiting call is listed.

// =======
// RED ZONE (R4, ADR 1; DRAFT awaiting the user's sign-off): the approvals
// waiting for the user (auto mode's consents) or a boss (super mode's
// appeals), kept in view.json so a restart re-shows them. Disk never says

export type Kind  = "consent" | "appeal";
export type State = "open" | "yes" | "no" | "cut" | "expired";
export type Pending = { id: number; kind: Kind; who: string; boss?: string; tool: string; args: string; reason?: string; fp: string; made: number; until: number; state: State };
export type Grant = { who: string; until: number };

export const GRANT_MS   = 30 * 60_000;
export const ARGS       = 32_000;
export const PENDS      = 50;

export function canon(x: unknown): string {
  const walk = (v: unknown): unknown => Array.isArray(v) ? v.map(walk)
    : v !== null && typeof v === "object" ? Object.fromEntries(Object.keys(v).sort().map((k) => [k, walk((v as any)[k])]))

}
